# BBVoxi v1.3.2 代码质量与稳定性审查报告

> 审查范围：`src/` 全部 15 个模块（约 9,671 行）。
> 审查方式：逐文件通读 + `cargo test` + `cargo clippy --all-targets` 实证验证。
> 结论先行：这是一份**工程质量明显高于平均水平**的代码库，绝大多数已知坑都已被
> 注释记录并用回归测试钉死。下面列出的是仍然存在的、值得进一步优化的点，按影响排序。

## 1. 稳定性问题（按影响排序）

### S1 ·【高】录音没有时长上限，Stop 事件一旦丢失就会永久录音
- 位置：`session.rs:289-366`（主录音 `select!` 循环）。
- 现状：正常录音「完全跟着按键走，不做时长限制」，循环的退出条件只有四个——
  收到 `Cmd::Stop`、麦克风自行结束、服务端 `done`、发送/接收出错。
- 风险链：`hotkey.rs` 自己的注释就指出 **Windows 会静默摘掉响应过慢的低级键盘钩子**。
  一旦钩子被摘或某次 keyup 丢失，`Cmd::Stop` 永远不来，`armed` 一直为真：
  **麦克风常开、音频持续推流到付费 ASR 接口、会话线程永不退出**，且界面毫无提示。
  这正是「按住说话」类工具最坏的失效模式（隐私 + 费用 + 卡死）。
- 现有缓解：托盘菜单「停止录音」可手动结束——但主人未必察觉。
- 建议：在主 `select!` 里加一条**安全上限分支**（如 3~5 分钟），到点自动收尾、
  写日志并通过 `notice` 提示「录音超时已自动结束」。这是性价比最高的一处加固。

### S2 ·【中】钩子被系统摘除后无健康监测、无自动重装
- 位置：`hotkey.rs:455-501`（`spawn` 安装 `WH_KEYBOARD_LL`）。
- 现状：钩子只在启动时装一次；消息循环出错（`GetMessageW` 返回 -1）会记日志并退出，
  但**退出后不再重装**，此后所有快捷键静默失效，只能重启程序。
- 与 S1 同源：系统因回调超时摘钩子时，程序这边完全无感。
- 建议：① 钩子线程退出后尝试重装（带退避）；② 或周期性自检钩子句柄有效性。
  完全检测「被系统摘掉」较难，但至少消息循环异常退出这条路径应当能自愈。

### S3 ·【低】`set_current` 与钩子线程之间的原子状态竞争
- 位置：`hotkey.rs:398-411`（UI 线程写）对比 `hook_proc:549-561`（钩子线程读-改-写）。
- 现状：`armed / held_vk / pending_win / session_win` 是四个独立的 `Relaxed` 原子量，
  钩子按「读四个 → 算 → 写四个」运作；`set_current` 在改键时从另一线程清零这四个量。
  两者交错时，钩子可能把**陈旧值写回**，覆盖掉刚做的清零。
- 影响：窗口极窄、且只在「用户改快捷键的瞬间正好有按键事件」时触发，后果是
  一次过期的 `armed`（录音停不下）或一次多余的 Win 补发。概率很低。
- 建议：把四个状态打包进**单个 `AtomicU64`** 一次读写，或改键时先 `paused=true`
  再清零（捕捉流程已经会 pause，可复用）。属锦上添花，非必须。

### S4 ·【低】音频错误回调里做磁盘 I/O
- 位置：`audio.rs:159-168`（`on_err` 里调用 `crate::log::log`）。
- 现状：`log()` 会抢锁 + 写文件。它跑在 cpal 的**错误回调**线程上。
- 影响：错误回调是终止性、低频路径（拔麦克风/设备独占），阻塞危害远小于数据回调，
  但与本项目在键盘钩子里「回调内严禁 I/O」的严格原则不一致。
- 建议：错误回调里只置原子标志/写内存，真正的日志交由会话线程补记（项目已有
  `take_replay_failures` 这一成熟范式可照搬）。

## 2. 安全性

### SEC1 ·【中】API 密钥以明文 JSON 落盘
- 位置：`config.rs:304-322`，存于 `%APPDATA%\BBVoxi\config.json`。
- 现状：千问/豆包 `api_key`、腾讯 `secret_key` 全部明文。任何能读到该文件的
  进程/用户都能拿到密钥。原子写、防损坏做得很好，但**没有静态加密**。
- 建议：用 Windows DPAPI（`CryptProtectData`/`CryptUnprotectData`）对密钥字段做
  按用户加密后再落盘。桌面应用常见加固，改动集中在 `config.rs` 的读写两处。

### SEC2 ·【低】腾讯签名 URL 含 `secretid`，注意别进日志
- 位置：`asr/tencent.rs:117-163`、`asr/mod.rs:475-506`。
- 现状：`secretid` 以明文查询参数出现在 signed URL 中（腾讯鉴权方案使然，
  真正的秘密 `secretkey` 不在 URL 里）。目前连接失败的 `context` 文案不含 URL，
  泄漏风险低；但 `into_client_request` 失败分支 `format!("非法接口地址：{url}")`
  会把整条 URL 带进错误链，最终可能落到日志。
- 建议：凡是要进错误链/日志的 URL，统一对 `signature`、`secretid` 做脱敏。

## 3. 性能与资源

### P1 ·【低】窗口隐藏且空闲时仍以 10Hz 持续重绘
- 位置：`main.rs:511`（`request_repaint_after(100ms)` 无条件每帧续期）。
- 现状：常驻后台时 UI 线程每秒醒 10 次轮询托盘事件，笔记本上有微小但持续的耗电。
- 建议：无会话且窗口隐藏时退避到 ~2Hz（或事件驱动），录音/捕捉期间再恢复 10Hz。

### P2 ·【信息】服务端帧通道满时丢帧，可能丢掉 final 包
- 位置：`asr/mod.rs:33,430-464`（容量 64，满则 `try_send` 丢帧并限流记日志）。
- 现状：设计正确（宁可丢帧也不阻塞读取任务）。极端情况下若被丢的恰是带 `done`
  的最后一包，会话会白等到 8 秒超时。概率很低，已有日志可查，无需改动，记录备查。

## 4. 代码质量与工程化

### Q1 ·【低】清理 16 条 clippy 警告并加 CI
- 现状：无 `.github/`，156 个测试这么好的资产没有自动门禁，全靠手动跑。
- 建议：加一条 GitHub Actions：`cargo clippy -- -D warnings` + `cargo test`。
  顺手修掉现存 16 条警告（`session.rs:640` 的 `bool::then` 多余闭包、
  `typer.rs:7-9` 文档缩进等），让 `-D warnings` 能长期保持绿色。

### Q2 ·【信息】注释密度极高
- 现状：大量「为什么这么写」的长注释，对维护是**显著加分**（很多坑被文字记录）。
- 唯一风险：超长注释与代码漂移。建议把「历史 bug 复盘」类长注释适当沉淀到
  `docs/`，源码注释保留结论性的一两句即可。非必须。

## 5. 值得肯定的设计（保持）

- **纯函数状态机 + 显式传参**：`hotkey::decide`、`ui::capture_step`、`typer::plan/diff`
  都把「碰系统的部分」隔离在外，使得最易错的时序逻辑可单测——这是本库测试覆盖率的根基。
- **锁中毒恢复**：`Shared::update`、`run_session`、`log()` 都用 `into_inner()` 取回数据
  继续跑并记日志，而不是静默 `return`。
- **超时无处不在**：连接 5s、发送 5s、收尾等结果 8s、麦克风就绪 5s、尾帧 300ms——
  「网络半死时绝不把常驻程序卡死」这条贯彻得很彻底。
- **原子配置写**（临时文件带 pid + rename）、**剪贴板 RAII Guard**（含 panic 展开路径）、
  **有界通道防内存膨胀**、**panic hook 落日志 + `panic=unwind`**——都是常驻程序该有的样子。
- **交付三态语义**（`typer::finish` 的 `Ok(true)/Ok(false)/Err`）逼调用方分别处理，
  从类型层面堵住了「结果被静默丢弃」。
