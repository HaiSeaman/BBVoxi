## 结论速览

| # | 现象 | 根因（一句话） | 处理 |
|---|---|---|---|
| 1 | 按住 Ctrl+Win 说话时"突然断开"，紧接着像只按着 Win 那样弹出开始界面 | 组合里的 Win 是按**后按的那个键**才被吞的；先按 Win、后按 Ctrl 时，Win 的按下已经放给了系统外壳，外壳于是看到一次**完整独立的 Win 按键**，松开时必弹开始菜单抢走焦点 | **改成"Win 的按下由我们全程接管、事后按真实意图补发"**，两种按键顺序都不再泄漏 |
| 2 | 提示"录音途中切换了窗口……已复制到剪贴板"时，设置窗自己弹出来 | 会话线程通过一个"请求显示窗口"的通道把设置窗顶到最前面 | **删掉该通道**；提示改走托盘悬浮文字 + 窗口内文字 + 日志 |

两条都不是猜的：先用 5 个注入探针在真机上把 Windows 的行为测清楚了，再动代码。探针产物已删除，结论见 §3。

## 一、"突然断开 + 弹出开始界面"

### 1.1 为什么是"断开"和"开始界面"同时出现

这两件事其实是**同一件事**的两半：

1. 松开组合里的任一修饰键 → 本次录音正常结束（这就是主人感觉到的"突然断开"——比预期早，因为焦点/节奏被打断了）；
2. 同一次松开里，Win 的 keyup 没有被我们吞掉 → 系统外壳把之前收到的 Win keydown 配上这次 keyup → **开始菜单弹出并抢走焦点**。

于是"松开手"的瞬间同时发生：录音结束 + 开始菜单跳出来。日志里 73 次录音、73 次松开，说明**会话从来没有自己中断过**，宿主侧一切正常 —— 问题全在"哪一次 Win 事件落到了外壳手里"。

### 1.2 根因：Win 的按下泄漏给了系统外壳

旧代码的规则是「**凑齐组合的那一次按下**才吞」：

| 按键顺序 | 旧行为 | 后果 |
|---|---|---|
| 先 Ctrl 后 Win | Win 的按下刚好是"凑齐"的那一次 → 被吞 ✔ | 正常 |
| **先 Win 后 Ctrl** | Win 的按下时组合还没凑齐 → **放行给外壳**；随后 Ctrl 的按下才凑齐 → 被吞 | 外壳记住"Win 按下过"；松开 Win 时（`held_vk` 记的是 Ctrl，匹配不上）→ 未被吞 → **开始菜单弹出** |

只要按下顺序不巧，就必然复现。这也解释了为什么是"经常"而不是"每次"——手指落键顺序本身就随机。

### 1.3 为什么"看起来更简单"的两条路都走不通（实测结论）

| 候选修法 | 实测结果 | 结论 |
|---|---|---|
| 把泄漏的 Win **松开**也吞掉（不改按下） | 开始菜单确实不弹了；但 `GetAsyncKeyState(VK_LWIN)` 一直是"按下"，此后**随便敲一个字母都会触发 Win+X**（自动打开资源管理器） | ✘ 换来了更糟的 bug |
| 一律吞掉 Win 的**按下**，等别的键来了再补 Win 的按下 | 补发**来不及**：外壳会先收到那个键（它以为 Win 没按下）→ 组合键失效，字母被当普通字符打出去 | ✘ 会弄坏 Win+E 这类系统快捷键 |

第一条是"按下放行、松开吞掉"，第二条是"按下吞掉、补发太晚"。两条都不行，剩下的唯一正解就是：

> **Win 的按下（含长按重复）一律由我们接管，随后按主人真正想干什么补发。**

### 1.4 修复内容

`hotkey.rs` 的判定函数新增两个记账字段（`Hold::pending_win` / `Hold::session_win`），三种结局：

| 主人实际想做什么 | 我们怎么做 |
|---|---|
| 组合凑齐了（Ctrl 也按下了） | 那次 Win 被**收编**进本次按住，按下与松开**全程照吞**，一次补发都不做 → 外壳什么也没看到，既不弹菜单也不留"Win 还按着"的假状态 |
| 只按了 Win 就松开（想打开开始菜单） | 吞掉原始松开，**补一整套 Win 按下+松开** → 开始菜单照常弹出，且系统里 Win 状态是干净的 |
| 按了 Win 又按了别的键（Win+E 这类组合键） | 吞掉那个键的原始按下，**一次 `SendInput` 提交「Win↓ + 该键↓」** → 系统组合键照常生效 |

按下顺序与结果无关：先 Ctrl 后 Win、先 Win 后 Ctrl，走的是同一条路。

配套的注入通道在 `injector.rs` 新增：`press_win()` / `win_then_key()`（事件序列单独抽成 `*_events()` 以便单测，单测里绝不真的注入 Win —— 那会当场弹出开始菜单）。

### 1.5 顺带堵住的两个洞（复审时发现）

- **录音途中的 Win 自动重复**：若此时又按了组合外的修饰键（组合因此不匹配），旧写法会把这次"重复"记成一笔新的待补发账，随后主人随手按的字母会被补发成 Win+X —— 等于凭空替他按了系统快捷键。现在录音开始后过来的 Win 事件只吞、不记账。
- **过期记账**：换键/改键捕捉结束的清理与按键事件理论上能挨在一起，留下"半截账"。现在补发额外要求"那次 Win **现在还按着**"，过期账一律不补。

## 二、这句提示不再弹窗

### 2.1 根因

会话线程发现"主人已经切走窗口"时，会调 `Shared::show_settings()` 置一个"请求显示窗口"的标志位，`App::logic` 每帧检查它并把设置窗顶到最前面 —— 于是主人正在别的程序里打字时，一个窗口自己跳出来。

### 2.2 修复

- **删掉整条通道**：`Shared::show_settings` / `take_show_request` / 那个原子标志位全部移除（连带它那条"必须放在 `Visible(false)` 之前"的时序注释），设置窗从此只由主人的动作打开（托盘、双击、`--settings`）。
- **提示落到不打扰的地方**：
  1. 托盘悬浮文字 —— `BBVoxi · 录音途中切换了窗口……已复制到剪贴板，按 Ctrl+V 粘贴`（提示优先于"上次出错"）；图标同时切到"该看一眼"那一档（图标只有就绪/录音中/出错三张图，不新增美术资源）；
  2. 窗口里的那一行字 —— 主人愿意打开设置窗时照样看得到，且用的是**提醒色**而不是错误色（这不是故障）；
  3. 日志 —— `提示（不弹窗，结果在剪贴板）：……`。
- 同一处理也用在"注入失败（比如目标程序是管理员权限）"那条路径上：结果照样进剪贴板，同样**不弹窗**（错误本身仍按错误记，托盘图标与悬浮文字都会说清楚）。

## 三、实测证据（5 个注入探针）

排障期间写了 5 个临时探针（`examples/`，用完已删）直接测 Windows 的真实行为。结论：

| 探针 | 问题 | 结果 |
|---|---|---|
| 1 | 注入孤立的 Win **松开**（没有按下）会不会弹开始菜单？ | **不会**（顺带排除"打字前注入的修饰键重置里有 Win keyup"这条嫌疑） |
| 1 | 注入完整的 Win 按下+松开 | **会**弹（且是在**松开后约 40ms**，确认开始菜单由 keyup 触发） |
| 2 | 外壳看过 Win 按下、我们把松开吞掉 | 菜单不弹，但系统状态**卡在"Win 按着"** |
| 3 | 钩子回调内部补发 Win↓ 再放行当前键 | **组合键失效**（补发不生效） |
| 3 | 一次批次提交 [Win↓, E↓, E↑, Win↑] | 资源管理器正常打开、且**不弹**开始菜单 |
| 4 | 只吞 Win↓ + Win↑（旧代码在"先 Ctrl 后 Win"时的行为） | 状态干净、后续键盘一切正常 |
| 4 | 放行 Win↓、只吞 Win↑ | 之后**随便敲个字母都会打开资源管理器** ⇒ 这条路否决 |
| 5 | 一次批次补发 [Win↓, E↓] 后，再放行真实的 Win↑ | Win+E 生效、不弹菜单、`GetAsyncKeyState(VK_LWIN)` 回到 0x0000（状态干净） |

## 六、已知限制（都是刻意保留的，不是漏改）

- **补发依赖 `SendInput`**：若当前前台是管理员权限的程序，注入会被 UIPI 拦下。此时"单独按 Win / Win+X"可能这一次没反应（日志里有 `补发 Win 按键失败`）。**录音本身不受影响** —— 录制路径一次补发都不需要，文字仍会照常进剪贴板。
- **组合里含 Win 时，Win 的按下由本程序接管**：与快捷键定义冲突的用法（例如自己另配一个 Win 相关的快捷键）会被本程序先吃掉，这是接管 Win 的必然代价。
- **钩子里不再有任何文件 I/O**：补发失败只累加原子计数与错误码，由会话线程在开新会话时
  落成日志（`hotkey::take_replay_failures` / `session::log_replay_failures`）。
  低级键盘钩子里的每一次耗时都很敏感（Windows 超时会**静默摘掉钩子**）——
  常规路径上的文件日志早就挪到会话线程了，这一处是随后的全量审查补上的。
- **托盘提示需要悬浮查看**：图标只有三张（就绪/录音中/出错），"结果已进剪贴板"借用了"出错"那一档图形。要更醒目需要新增一套美术资源，本次没做（主人明确要求"别弹窗"，所以选了最不打扰的方式）。
