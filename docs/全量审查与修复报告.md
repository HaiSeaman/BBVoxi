## 2. 修掉的问题（按严重度）

### 2.1 【严重】会话线程可能被永久卡死

- `audio.rs::start()` 用 `ready_rx.recv()` **无超时**地等设备就绪，而它是同步调用、跑在会话线程上。
  设备被独占或驱动卡死时（WASAPI 常见），整个会话线程卡住 → 之后**所有热键失效**（连"松开结束"
  都收不到），界面永远停在"录音中"，只能重启程序。
- **修法**：加 5 秒上限，超时就如实报错并请采集线程收工（`DEVICE_READY_TIMEOUT`）。

### 2.2 【严重】主人自己设的快捷键会被悄悄改回默认值

- `config.rs` 的旧默认值迁移（Ctrl+反引号 → Ctrl+Win）**每次启动都跑**：主人升级后如果把快捷键
  设成 Ctrl+反引号，下次启动会被静默改回 Ctrl+Win，界面上一个字都不提。原有测试
  `migration_leaves_user_hotkeys_alone` 的清单里恰好漏了这一项，所以一直没被发现。
- **修法**：迁移只在 `version < CURRENT_VERSION` 时执行；补回归用例
  `migration_never_overwrites_a_current_config`。

### 2.3 【中】钩子回调里做文件 I/O（违反仓库自己的不变量）

- `hotkey.rs` 两处补发失败时直接调 `log::log` —— 低级键盘钩子必须毫秒级返回，一旦卡住会被
  Windows **静默摘掉**（表现就是"快捷键全失效、Win 键开始乱弹"且日志为空）。
- **修法**：钩子里只累加原子计数与错误码；日志由会话线程在开新会话时补记
  （`hotkey::take_replay_failures` / `session::log_replay_failures`）。

### 2.4 【中】窗口里的结论与提示自相矛盾（承诺说"留住了"，其实没留住）

- 结果卡片那句"这份结果也留在了剪贴板"只看"开关开着 + 有结果"，**不看写入是否核对通过**；
  于是复制失败的那一次也照样这么说 —— 主人照着 Ctrl+V 什么也粘不出来，正是他报的那个坑
  从弹窗搬进了窗口。
- **修法**：剪贴板交付收成唯一入口 `session::put_on_clipboard`（写 + 回读核对 + 记录结果），
  新增 `Snapshot::kept_on_clipboard` 只由核对通过置位；窗口那句、托盘提示、状态胶囊都以它为准；
  失败时用不同的说法（"但没能复制到剪贴板（原因）"）。

### 2.5 【中】会话中途失败时一个字都不留

- 网络超时、麦克风异常这些中途失败路径直接 `fail` 返回，剪贴板里什么都没有 ——
  与"识别结果留一份"的承诺矛盾。
- **修法**：`session::keep_partial_on_failure`，把已识别到的部分也留一份（留不到就写日志）。

### 2.6 【中】尾帧可能丢：靠"固定睡 60ms"等补发

- 停止后再收干音频前固定睡 60ms，而采集回调周期在蓝牙免提/部分 USB 声卡上能到 100ms 以上 →
  流被 drop 掉时尾帧还没补发，主人松手前那几个字就丢了。
- **修法**：采集侧在补发完（或无残留可补）时置位 `Capture::tail_flushed`，会话侧**等这个标志**
  （上限 300ms）；两端都有界，谁也不会为尾巴卡死。新增 2 条单测。

### 2.7 【低】其余四处

| 位置 | 问题 | 修法 |
|---|---|---|
| `hotkey.rs` 钩子线程消息循环 | `GetMessageW(..).as_bool()` 把 -1（出错）当成"还有消息"→ 空转刷 CPU，钩子其实已失效且一声不响 | 按 `>0 / 0 / -1` 分别处理，出错记日志后退出 |
| `asr/mod.rs::close()` | 死函数（带 `#[allow(dead_code)]`）：注释写着"让服务端看到正常关闭"，却从没人调用 | 收尾时真正调用它（失败只记日志，不影响结果） |
| `asr/doubao.rs` 解压 | `read_to_end` 无上限，异常帧可能把常驻进程的内存吃光 | 8MB 上限，超出按"这帧解不出来"处理 |
| `log.rs` | 单测往**主人真实的日志文件**里写（日志里 205 条假的"主人切到了别的窗口"，排查时把我自己都带偏过） | `cfg!(test)` 只写 stderr、不碰文件；同时删掉那条"恒真"的校验用例 |
| `assets/77db….png` | 与 `docs/界面截图.png` **字节完全相同**（md5 一致）的重复素材 | 删除（git 里有记录，可随时找回） |

### 2.8 重用与结构（去掉重复/多余抽象）

- `CaptureHandles`：采集的四个共享句柄以前成串穿四层调用（`start` → `build_stream` → `build` → `Feed`），
  加一个字段要改四处、还容易传错位置。
- `after_keyup()`：`decide` 的 keyup 分支以前各重列七个字段，漏一个就是静默的行为差异。
- `foreground_is_own()`：两处各自写了一遍"取前台窗口 + 判是不是自己"。
- `Fallback` 单字段结构体（Middle Man）→ `with_paste_fallback(bool)`；方法改名
  `paste_via_clipboard`（避免与字段同名）。
- 上一轮已删：剪贴板"先存后还"整套机制（`OriginalClipboard` / `should_snapshot` /
  `schedule_restore` / `sequence`）。

## 3. 刻意**不**改的（判断 + 理由）

| 审查建议 | 为什么不动 |
|---|---|
| `Hold` 的 `u32` + `0` 哨兵换成 `Option<NonZeroU32>` | 这些值要进出 `AtomicU32`，换类型只在边界增加转换；而虚拟键码 0 物理上不存在，"0 = 没有"没有歧义。风险大于收益 |
| `press_win` / `win_then_key` 拆成 `*_events` + 发送两步 | 留：单测**不能**真的注入 Win 按键（会当场弹出开始菜单），拆分正是为了可测 |
| qwen / tencent 的 `audio_messages` 各一行相同 | 不抽：单行表达式，抽出来只是多一层转发（Middle Man） |
| `(vk, scan, extended)` 打包成结构体 | 不抽：只有 1 个调用点，且这个参数形状本就对应 Win32 的 `KEYBDINPUT` |
| ui 的三处圆点绘制、两个按钮助手合并 | 不合并：纯样式重排会把 0.5px 的观感差异改掉，而沙箱里没法截图核对 UI —— 不值得为省 4 行冒视觉回归 |
| `dirs` 依赖换成 `%APPDATA%` | 保留：它确实在用（`config_dir()`）；换掉只是少一个依赖，却要自己处理非 Windows 分支与变量缺失 |
| `dist/*.exe`（未跟踪的打包产物） | 保留：主人的发布流程要用（其中一个还是给主人实机验证的测试版） |
| `untitled-project/` | 只报告：仓库根目录下一个**未跟踪的嵌套空 git 仓库**（含 `.commandcode/taste/taste.md`），是与本项目无关的脚手架残留。不是我的东西，删不删由主人定 |
| `assets/3fbe….png`（未被任何文件引用的候选原图） | 只报告：这是美术素材（`make_icons.py` 的源图是命令行传参、不固定引用它），是不是还要留着由主人定 |

## 4. 必须披露的一次事故

审查子代理为了强制重编译执行了 `git checkout -- src/main.rs`，**抹掉了我尚未提交的 main.rs 改动**。
它随后按最初读到的原文手工还原。我已用 `git diff HEAD -- src/main.rs` 逐行核对：`sync_tray` 的
notice 分支与提示语、`logic()` 里去掉"请求弹窗"的两处改动都在，`cargo check` 通过。

两条教训（已写进项目记忆）：
1. **派子代理做审查时，prompt 里必须硬性禁止一切写操作**（这次只写了"只读"，它仍然动了 git）；
2. **未提交的工作树是唯一副本** —— 主人手上的这些改动建议尽快 `git add -A && git commit`，
   未提交状态经不起这种事故。
