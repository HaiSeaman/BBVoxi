# 豆包（火山引擎）语音识别报错修复报告

- 日期：2026-09-11
- 影响版本：v1.1（豆包服务商实际从未可用）
- 涉及文件：`src/asr/doubao.rs`、`src/asr/mod.rs`（仅加 `#[derive(Debug)]`）、`README.md`

---

## 一、现象

切到「豆包（火山引擎）」后，一开始录音就报错，且报错内容里看不到任何有用信息：

```
豆包返回错误（code=-1）：{"result":{"additions":{"log_id":"20260911021814ACCB668A3BD12A68B5F1"}}}
```

---

## 二、根因

不是鉴权问题，也不是 Key 或资源 ID 的问题，**是我们的响应解析按了一套火山 v3 并不存在的结构去写的**。

用真实连接抓帧（忽略测试 `live_probe_dump_frames`）拿到的服务端返回：

```
[帧] type=0b1001 flags=0b0000 正文：{"result":{"additions":{"log_id":"20260911023351…"}}}
[帧] type=0b1001 flags=0b0011 正文：{"audio_info":{"duration":2100},"result":{"additions":{"log_id":"…"}}}
[非二进制帧] Close(reason="finish last sequence")
```

对比我们原来的假设：

| 项 | 原代码假设 | 火山 v3 实际 |
|---|---|---|
| 响应正文顶层 | 有 `code` 字段 | **没有 `code`**（顶层是 `audio_info` / `result`） |
| 文本位置 | `payload_msg.result` | **`result`**（正文本身就是 payload_msg，没有这层包装） |
| 结束标记 | JSON 里的 `is_last_package` | **帧头 flags 的 `0b0010` 位**（实测末包 flags=0b0011） |
| 错误码 | JSON 里的 `code` | **错误帧（msg_type `0b1111`）帧头**：`code(4B)+size(4B)+正文` |

于是两个叠加的错误：

1. `parsed["code"].as_i64().unwrap_or(-1)` —— 字段根本不存在，兜底成 `-1`，
   `-1 != 0` 判定为「出错」。**服务端的每一条正常响应都被当成了错误**，
   建连后立刻下发的那条空结果帧就是用户看到的那条报错。
2. 即便没被误判，`payload_msg.result` 也永远取不到文本，识别结果始终为空。

顺带说明：日志/`log_id` 看着像错误，其实 `result.additions.log_id` 是火山在正常响应里回传的链路追踪 ID。

---

## 三、修复内容

### 1. `decode()` 按官方协议重写

返回 `Frame { msg_type, flags, code, payload }`，拆帧顺序与官方文档一致：

```
header(4B) → [序号 4B  if flags & 0b0001]
           → [事件 4B  if flags & 0b0100]
           → [错误码 4B if msg_type == 0b1111]
           → 长度 4B → 正文（按压缩位决定是否 gzip）
```

- 头长度改为从 `bytes[0] & 0x0f` 读（原来写死 4）
- 补上 `flags & 0b0100`（事件号）的偏移
- 错误帧单独走「先读 code 再读 size」的分支
- 无序列化（纯文本）的正文不再被当成解析失败丢掉

### 2. `parse()` 判定逻辑改对

```rust
let json_code = frame.payload["code"].as_i64().unwrap_or(0);   // 缺失 = 0 = 成功
if frame.msg_type == MSG_ERROR_RESPONSE || frame.code != 0 || json_code != 0 { … }
```

- **字段缺失按成功处理**，只有「错误帧 / 帧头 code≠0 / JSON 显式 code≠0」才报错
- 文本改从 `frame.payload["result"]` 取
- 结束标记改成 `frame.flags & FLAG_LAST_PACKET`

### 3. 错误信息可读化

`describe()` 现在输出 `豆包返回错误（code=45000002，空音频）：…`，附带官方错误码中文对照：

| code | 含义 |
|---|---|
| 45000001 | 请求参数无效 |
| 45000002 | 空音频 |
| 45000081 | 等包超时 |
| 45000151 | 音频格式不正确 |
| 55000031 | 服务器繁忙 |
| 55xxxxxx | 服务内部错误 |

### 4. 测试

新增 4 个单测（共 59 个全过）：

- `handshake_frame_without_code_is_not_an_error`：用**线上抓到的那条真实帧**做回归，确保空结果帧不再被误判
- `last_package_flag_marks_finished`：末包靠 flags 结束
- `error_frame_code_comes_from_header`：错误码从帧头读，并带上中文解释
- `non_zero_code_is_an_error`：JSON 显式 code 仍要报错

另外保留了一个 `#[ignore]` 的探测测试 `live_probe_dump_frames`，
豆包协议再变时可以直接抓真帧排查（设 `BBVOXI_DOUBAO_KEY`，可选 `BBVOXI_DOUBAO_WAV` 喂裸 PCM）。

## 四、验证

真实连接 + 4.2 秒中文语音（TTS 生成后转成 16k/16bit/mono 裸 PCM）端到端跑通：

```
[帧] flags=0b0001 … "text":"你好"                        → Partial「你好」
[帧] flags=0b0001 … "text":"你好，这"                     → Partial「你好，这」
…
[帧] flags=0b0001 … "text":"你好，这是一段测试语音，今天天气不错" → Partial
[帧] flags=0b0011 … definite:true, source:"two_pass"     → Final「你好，这是一段测试语音，今天天气不错。」
[Close] finish last sequence                              → Finished
```

- 中间结果持续推送（实时输入可用），末包二遍识别给出定稿文本，标点由服务端补上
- 全程无报错
- 顺带确认：音频帧不带序号、不 gzip 服务端照样收（`audio_info.duration` 与实际发送时长一致），无需改发送侧
