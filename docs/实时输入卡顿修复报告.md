# 实时输入卡顿修复报告

日期：2026-09-10 第六轮

---

## 一、根因：打字前有 1.5 秒的阻塞等待（日志实测证据）

### 证据

`%APPDATA%\BBVoxi\logs\bbvoxi.log` 里的真实记录：

```
[1789038548] 快捷键按下 → 开始录音
[1789038550] 等待修饰键松开超时，仍按当前状态输入   ← 每次打字前卡 1.5 秒
[1789038551] 等待修饰键松开超时，仍按当前状态输入
[1789038553] 等待修饰键松开超时，仍按当前状态输入
[1789038555] 等待修饰键松开超时，仍按当前状态输入
[1789038556] 等待修饰键松开超时，仍按当前状态输入
[1789038558] 等待修饰键松开超时，仍按当前状态输入
[1789038558] 快捷键松开 → 结束录音
```

这一场录音从 548 到 558 共 **10 秒，其中 6×1.5s = 9 秒纯等待**。日志里累计出现 12 次。
这就是"一卡一卡、有时候卡住好久才出字"的全部原因。

### 为什么会这样

我上一轮为防止 `Ctrl+A` 之类误触发，在每次注入前加了"等修饰键松开（最多 1.5 秒）"。
但**按住说话时用户正一直按着 Ctrl** —— 这个等待永远等不到，于是：

1. 每个中间结果都要先卡 1.5 秒才打字 → 明显卡顿
2. 更糟的是它发生在会话主循环里，**把音频发送也一起堵住了** → 识别服务收到的音频出现空档 → 出字更慢更碎

---

## 二、修复：注入前"清掉"修饰键（业界成熟做法）

### 依据

StackOverflow 上同类问题（"热键包含 Ctrl，用户仍按着时 SendInput 失效"）的公认解法，要点：

1. 注入前补发修饰键的 **KEYUP**，让前台程序认为修饰键已松开
2. **左右键都要发**（只发 `VK_CONTROL` 无效）
3. 右键是扩展键，要带 `KEYEVENTF_EXTENDEDKEY`
4. **必须与文本放在同一次 SendInput 调用里**，否则修饰键消息会重新插回消息队列

### 我们的实现（`src/injector.rs`）

```rust
const MODIFIER_RESETS: [(VIRTUAL_KEY, bool); 8] = [
    (VK_LCONTROL, false), (VK_RCONTROL, true),
    (VK_LMENU,    false), (VK_RMENU,    true),
    (VK_LSHIFT,   false), (VK_RSHIFT,   true),
    (VK_LWIN,     true),  (VK_RWIN,     true),
];
// 每个注入批次（打字 / 退格）开头先追加这 8 个 KEYUP，和文本同批发出
```

**为什么必须清修饰键**：不只是为了避免 `Ctrl+A`。我们的自动纠错要发**退格**，而退格是 VK 键——`Ctrl+退格` 在很多程序里是"删掉整个词"！
所以不清修饰键时，识别一修正就可能一次删掉一整段文字。这个隐患一并修掉了。

同时**彻底删除了 1.5 秒阻塞等待**，注入变成纯 SendInput（亚毫秒级）。

