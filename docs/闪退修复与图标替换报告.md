日期：2026-09-10

---

## 一、严重 Bug：点「测试麦克风与连接」软件直接闪退

### 1. 定位过程（先证据、后结论）

| 步骤 | 做法 | 结果 |
|---|---|---|
| ① 看现有证据 | 读 `%APPDATA%\BBVoxi\logs\bbvoxi.log` | 日志最后一行是「麦克风已启动」，**之后什么都没有**——既没有连接成功记录，也没有我们捕获的错误日志 |
| ② 推断 | 代码里连接失败会走 `shared.fail()` 并写日志；没写日志说明进程没走到那里 | 崩溃点在 `AsrClient::connect()` 内部，且是**进程级死亡** |
| ③ 解释「为什么没有任何提示」 | 查 `Cargo.toml` | release profile 里有 `panic = "abort"` → 任何 panic 都变成**静默退出** |
| ④ 复现 | 写回归测试：用无效 Key 调用 `AsrClient::connect()`（走真实 TLS 路径） | 精确复现 panic |

复现得到的报错原文：

```
panicked at rustls-0.23.44/src/crypto/mod.rs:249:
Could not automatically determine the process-level CryptoProvider from Rustls crate features.
Call CryptoProvider::install_default() before this point to select a provider manually,
or make sure exactly one of the 'aws-lc-rs' and 'ring' features is enabled.
```

### 2. 根因

`tokio-tungstenite` 的 `rustls-tls-webpki-roots` 特性**只启用了 TLS 传输层，没有启用任何加密后端**（ring / aws-lc-rs 都没开）。rustls 0.23 在首次建立 TLS 连接时会尝试自动选择加密后端，选不出来就 panic。

而「测试麦克风与连接」是**第一次真正发起 WSS 连接**的地方（平时要点快捷键才会连），所以：
- 现象 = 点测试按钮 → 立刻闪退
- 影响面 = **三家服务商全部**（不只是千问），因为都走 WSS
- 为什么看起来像「点了按钮就没了」= `panic = "abort"` 让进程直接终止，没有任何弹窗

### 3. 修复

1. `Cargo.toml` 显式启用加密后端：`rustls = { features = ["ring", "std", "tls12", "logging"] }`
2. `src/asr/mod.rs` 增加 `ensure_crypto_provider()`，在任何连接前安装进程级加密后端（幂等）

### 4. 顺带修掉的三层防护（让同类问题不再「找不到线索」）

| 层 | 改动 | 作用 |
|---|---|---|
| 日志 | `install_panic_hook()`：panic 的文件、行号、消息写入日志 | 以后再崩，日志里有确切位置 |
| 编译 | release 去掉 `panic = "abort"`，改回 unwind | 后台线程 panic 不会带走整个程序 |
| 运行 | 会话过程用 `catch_unwind` 包裹 | 单次识别出异常只结束本次会话，程序继续跑并提示用户 |

### 5. 验证

- 回归测试 `connect_with_invalid_key_returns_error_instead_of_crashing`（永久保留）：修复前 panic，修复后返回明确错误 ✅
- 全量测试 **34 passed / 0 failed**
- release 实机启动冒烟：无 panic、日志正常、托盘正常 ✅

## 二、图标替换（这张图 → 全软件所有图标）

### 1. 图片处理：两个真实坑

**坑 1：不能"接近白色就算透明"**
第一版用「亮度接近白 → alpha」公式反推，结果图案**内部的白色高光被一起挖空**，整体发灰发暗。
→ 正确做法：抓住棋盘格的**色签名**（实测纯白 ≥242、浅灰 ≈224，且彩度接近 0）判定背景；对**被图案围住的**背景区域（比如 V 的开口）靠色签名识别，对外部边缘靠洪水填充，这样图案内部带色偏的高光（彩度 ≥25）被完整保留。

**坑 2：Pillow 的 floodfill 在只读图上会"静默失效"**
`Image.fromarray(...)` 生成的图像是只读的，`ImageDraw.floodfill` 对只读图**既不报错也不填充**。这导致 `outside` 实际是 0%、背景残留大量噪点和细线。
→ 修复：先 `.convert("L")` 并把 `readonly = False`，洪水填充才真正生效。

### 2. 生成的资源（`scripts/make_icons.py` 一键可重跑）

| 文件 | 用途 |
|---|---|
| `assets/icon.ico` | 16/24/32/48/64/128/256 七尺寸，32 位带透明通道 |
| `assets/rgba128_window.bin` | 设置窗标题栏 / 任务栏 / Alt+Tab 图标（128×128 原始 RGBA） |
| `assets/rgba32_idle.bin` | 托盘·待机 |
| `assets/rgba32_rec.bin` | 托盘·录音中（右下角红点） |
| `assets/rgba32_err.bin` | 托盘·出错（右下角橙点） |

### 3. 接入方式

| 位置 | 实现 |
|---|---|
| exe 文件图标（资源管理器/任务栏固定） | `build.rs` 调 Windows SDK 的 `rc.exe` 编译 `assets/bbvoxi.rc`，把图标链接进 exe；**未引入任何新依赖**，找不到 rc.exe 时只告警不中断构建 |
| 窗口标题栏 / 任务栏按钮 / Alt+Tab | `ViewportBuilder::with_icon(128×128 RGBA)` |
| 托盘（含最小化隐藏后） | `tray-icon` 的三态 32×32 RGBA（空闲=原图，录音中/出错=原图+状态圆点） |
| 悬浮条窗口 | 同样挂 128×128 图标 |

### 4. 验证（机械校验，不靠肉眼）

用 `pefile` 解析 PE 资源表：

```
target/release/bbvoxi.exe → {'RT_ICON': 7, 'RT_GROUP_ICON': 1}
target/debug/bbvoxi.exe   → {'RT_ICON': 7, 'RT_GROUP_ICON': 1}
```

7 个 `RT_ICON` 正好对应 ICO 里的 7 个尺寸，`RT_GROUP_ICON` 是图标组头 ✅

## 四、需要你实机确认

1. 双击 `target/release/bbvoxi.exe` → 资源管理器里图标是否变成新图（透明底）
2. 打开设置窗 → 标题栏 / 任务栏是否为该图标
3. 托盘区图标是否为该图标；**按住快捷键录音时右下角出现红点**
4. 点「测试麦克风与连接」→ 是否还会闪退（**这是本次修复的重点**）
5. 说一句话，看设置窗「最近识别」是否出文字

若仍有异常，请把 `%APPDATA%\BBVoxi\logs\bbvoxi.log` 发我——现在任何 panic 都会带文件行号写进这个日志。
