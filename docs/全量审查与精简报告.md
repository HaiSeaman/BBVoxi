## 一、修复的真实 Bug

### ① 按住快捷键说话时前台疯狂出现 `111111`（本轮主 Bug）

**根因**：上一轮为消除卡顿，我在注入前会补发修饰键 KEYUP（把 Ctrl「清掉」）。
这些是我们**自己注入**的事件，而键盘钩子在**更新修饰键状态时没有过滤注入事件** ——
钩子把自己发的 Ctrl-up 当成了"用户松开 Ctrl"，于是 `mods_ok` 判定失败，
触发键**不再被吞掉**，用户长按 `1` 的自动重复全部漏给了前台程序。

**修复**：注入事件在进入钩子时直接放行、完全不处理（既不参与状态跟踪，也不参与判定），
并给我们注入的每个事件打上 `dwExtraInfo` 标记做双保险。

```rust
if ignore_event(injected || ours, paused) {
    return CallNextHookEx(...);   // 自己发的事件不参与任何判断
}
```

回归测试：`repeated_keydowns_while_holding_are_all_swallowed`（模拟 20 次自动重复，断言全部吞掉）、
`injected_events_and_pause_are_ignored`。

### ② 收尾可能把已经打出来的字删掉（数据丢失）

`take_result()` 原逻辑「有定稿就只用定稿」。若最后一句没等到定稿（超时 / 连接中断），
返回文本会**短于**已经写进目标程序的文本，收尾对账时就会退格删掉用户看到的字。

**修复**：改为「定稿 + 未定稿尾段」合并，并抽成纯函数 `merge_result()` 加测试
（`merge_result_keeps_unfinalized_tail`）。

### ③ 实时输入失败时界面状态错误

实时打字失败（例如目标窗口拒绝注入）时调用了 `shared.fail()`，它会把 `recording` 置为 false ——
于是**录音还在继续，界面却显示"没在录音"**。新增 `Shared::report()`：只报错、不动录音状态。

## 三、审查通过的部分（逐项核对过，无问题）

- **音频**：48k→16k 盒式重采样（实测每周期输出 1600 样本、峰值 ±1）、100ms 分帧、采集线程独立于 tokio
- **千问协议**：`run-task` → 二进制音频 → `result-generated`（`sentence_end` 区分中间/定稿）→ `finish-task`；心跳包被正确忽略

- **注入**：`KEYEVENTF_UNICODE` 代理对拆分、错误码 `5`（权限不足）单独提示、修饰键重置与文本同批次
- **日志**：10 万行上限滚动 + 多实例串行化
- **配置**：默认可反序列化旧文件、开关项即时生效（快捷键保存即生效）
- **界面**：深浅两套配色均有对比度断言
